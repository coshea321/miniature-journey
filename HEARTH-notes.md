- **v406:** **Fix: bringing an item back from the Done section never fed the list's history (Cathal 09/08/2026: "when I re-add something from the Done section it doesn't get added as an entry in the history"). Small and well-defined — this would have been fine on plain Sonnet.** **The gap was that v342's "a revive is a re-purchase" rule was only ever applied to ONE of the five ways an item can come back.** History is written exclusively by `addToHist` / `addToHistFor`, and `addItemToCurrent` (typing a name that matches something sitting in Done) is the only revive path that called it. Everything else flipped `done` to false and saved: **`toggleItem` (untapping the tick in the Done section — the one Cathal hit), the home quick-pick, the recipe "add ingredients" pass and the pasted-list import.** The last three are the clearest tell that this was an oversight rather than a decision — in each of those functions the *new-item* branch calls `addToHistFor`/`addToHist` and the revive branch two lines above it doesn't. Consequence: the item's History entry kept its old count and old `dates` series (so the v303 replenishment clock never reset for anything you habitually tick and untick), and an entry deleted from the History tab stayed deleted, because `clearHistTomb` only runs from inside `addToHist`. **Scope was confirmed via AskUserQuestion before building, and two paths were deliberately left OUT:** ① **Reopen all / Unpack all** — one tap would bump the count and stamp today's date on every done item at once, which would wreck the replenishment signal wholesale; ② **`togglePersonCheck`** (a travel item comes back to unpacked when one person unticks their circle) — that reads as correcting a tick, not as needing the thing again. **New guard, `reviveWasMisclick(it)` + `REVIVE_HIST_GRACE_MS = 60000`:** unlike the typed re-add, an untick is one tap away from a tick, so ticking something by mistake and immediately untapping it would otherwise inflate "Added Nx" by one every time. Items already stamp `updated` when ticked done, so the guard is a pure read of that with no new state — **and every call site must read it BEFORE `updated` is re-stamped**, which is why each of the four sites captures a local flag on the line above rather than checking inline. Only the count is at stake either way: `histRecordDate` already dedupes the date series per day. **Two ordering details that are load-bearing:** ⓐ in `toggleItem` the `addToHist` call sits at the very END of the loop body, after the v361 repeat block, and reads a `_wasRevived` flag captured before anything mutates — a repeating task's tick also sets `done` back to false, and a naive "done is false now" check would log every recurring completion as a re-purchase (pinned by a test); ⓑ the recipe and paste paths pass **`existing.name`, not the parsed `clean` name**, and run after `catId` settles — grocery matching is fuzzy (`groceryNameKey`), so a pasted "eggs" can land on an item stored as "Egg", and history/`capHistToLiveLimit`/the History tab's in-list check all compare on the exact stored name. **Tests: new `tests/cases/37-revive-history.js` (18 assertions), no existing test file touched.** The guard as a pure function incl. null-safety; the untick revive bumping count, refreshing `lastUsed`, appending today to `dates`, **creating an entry that didn't exist at all** (a synced-in or pruned item), and resurrecting a tombstoned entry; then the three negatives — ticking done, the repeat reschedule, and a tick undone inside the grace window; plus the v342 typed path still returning `"restored"` and still feeding history. **Verified non-vacuous, and the first draft was not:** referencing the new helper directly threw a `ReferenceError` on the old code and skipped every behaviour assertion, so section 1 now calls through a stub — on the pre-fix build it fails cleanly at 2a/2b/2c/2e/2g (count stuck at 3, dates stuck at `["2026-01-01"]`, the missing entry still `undefined`) while the section-3 negatives pass, which is the right shape: the pins are the fix, the negatives are guardrails. **40/40 files green.**
- **v405:** **Cook-along ticks — tap any ingredient or step in a recipe and it greys out; re-entering the recipe clears them (Cathal 07/08/2026: "is it possible to click on any part of a recipe so that it gets greyed out after it has been completed, but everything gets reset when you reenter the recipe?").** **Two design calls confirmed via AskUserQuestion before building:** ① **everything you *do* is tappable** — ingredient lines, Prep steps and Method steps — while the title, Serves, Notes and Source stay inert, because they're reference rather than tasks; ② **leaving the Recipes tab and coming back KEEPS the ticks** — only tapping "← All recipes" (or opening a different recipe) clears them, so glancing at the calendar mid-cook doesn't lose your place. **The state is deliberately display-only: `_recipeDone` / `_recipeDoneId` are in-memory module globals, never written to a recipe and never synced.** This is "where am I in tonight's cook", not a property of the recipe — persisting it would mean a partner opening the same recipe sees half of it struck through, and it would need a sync field, a merge rule and export/import handling for something that is over when dinner is. It also means a full app reload clears the ticks, which is the right trade and is stated in the on-screen hint. **Keys are positional (`i3` from the ingredient's index in `r.ingredients`, `p0`/`m2` from document order within the Prep/Method block) precisely so a re-render repaints the same ticks** — a servings change, a favourite toggle and an incoming sync push all rebuild `renderRecipeDetail` from scratch, and losing the ticks on any of those would make the feature useless mid-cook (all three pinned by tests). **Three implementation details that are load-bearing and must not be "tidied":** ⓐ **the delegated click listener is wired ONCE behind `_recipeTickWired`** — `#recipesContent` is a permanent element whose innerHTML is replaced, so a per-render `addEventListener` stacks a listener on every servings tap and a click then toggles N times, which reads as "the tick doesn't work" on even counts (this was written wrong first, caught before committing, and is now pinned by a test that re-renders three times and taps); it follows the existing `_tidyInputWired` / `_grocPickWired` pattern. ⓑ **`wireRecipeTicks` marks up the Prep/Method blocks AFTER innerHTML, rather than changing `formatMethod` / `derivedPrepHtml`** — those are shared string builders and marking them up in place would leak cook-along classes into anything else that ever renders a method. ⓒ **the tap toggles the class in place instead of re-rendering**, so the page never moves under your hands. `formatMethod` closes and reopens its `<ol>` around a sub-heading, so the `"ol > li, p"` selector walks document order across BOTH lists and the keys run on rather than restarting (pinned — restarting would grey a step above the one you tapped). - **v402:** **Prep-helper replies move OFF JSON to a quote-free "=== id" block format (Cathal 07/08/2026: "the json that a new chat comes back with quite often doesn't work first time and is not easily copyable", with the failing reply attached).** **Root cause found in his paste in seconds and confirmed by running it through a parser:** the reply contained `"prep":"...slice thinly into ⅛" slices on a mandolin..."` — **an unescaped inch mark, which closes the JSON string** and rejects the entire paste (`Expecting ',' delimiter`). This is not a rare slip: inches, `9x5"` tins and quoted names are ordinary in recipe text, so **asking a model to remember JSON escaping mid-recipe is a losing battle** — the format was changed rather than another rule added to the prompt. **New format: `=== <id>` on its own line, then one prep step per line, blank line between blocks.** No quoting, no escaping, nothing to get wrong; `"`, `'` and `\` are all just text. It also answers the second half of his complaint — one enormous single-line JSON blob is horrible to select on a phone, a line-based block is not. **And it degrades gracefully where JSON could not: a reply cut off part-way still imports every COMPLETE block before the cut** instead of failing outright, which matters given the truncation history in v398/v399 (pinned by a test). **`parsePrepReply` routes on the marker** — a paste containing a `=== <digits>` line goes to the new `parsePrepBlocks`, everything else falls through to **the JSON path, kept unchanged**, so a reply already in flight in a chat window is never stranded. The book-matching half was extracted into **`matchPrepEntries(list)`** so both formats share one implementation (id first, name fallback, one row per recipe, unmatched reported) — behaviour-preserving for the JSON path. `RECIPE_PREP_FILE_TAG` still exists and still gates that fallback; it is simply no longer mentioned in the prompt. - **v401:** **Duplicate-recipe finder and repair (Cathal 06/08/2026: "I would like to solve the duplicate issue"; v400 fixed the cause, this clears what the old id generator already created).** **Three design calls confirmed via AskUserQuestion first:** ① group by **same id AND same name** (not one or the other); ② unwanted copies are **deleted with tombstones**, like the Delete button, not local-only; ③ **suggest the fullest copy, he confirms**. **Two group kinds, deliberately distinct on screen because they're different problems:** `"id"` — records sharing an id, the v400 importer bug, where only the first was ever reachable by `find()`/`findIndex()` so the twins couldn't be opened, favourited, deleted or given prep; `"name"` — same name, different ids, two genuinely working records you probably only want one of. **A record belongs to exactly ONE group** — anything already in an id group is not also offered as a name duplicate, or resolving one group would silently change another (pinned by a test with a book that is both). **`recipeRichness(r)`** scores what a record actually carries (ingredient count, prep, notes, URL, category, fav, rotation, plus bonuses for v366-canonical bracketed ingredients and hand-set v368 grocery prefs) and only ever **suggests** a keeper — the fullest copy is usually the one that's been worked on, which is exactly the asymmetry in Cathal's book where one copy was tidied and the twins were raw. **Entry point is a self-hiding banner on the recipe list, not a fifth toolbar button** — this is a one-off repair, not a tool you reach for, and it disappears the moment the book is clean (the v362 "New week — plan dinners?" shape); it counts extra COPIES, not groups, and is suppressed in select mode. **Two things in `applyDupRepair` are load-bearing and must not be "simplified":** ⓐ it operates on **`_dupState.book`, the snapshot the choices were reviewed against, NOT a fresh `getRecipeBook()`** — that function re-parses from storage on every call and hands back new objects, so identity comparisons against the reviewed records all miss and nothing is ever deleted (this was a real bug during the build, caught by the tests); a **length-mismatch guard** aborts with a toast if the stored book changed mid-review rather than deleting by stale index. ⓑ **a tombstone is written only for an id that is genuinely leaving the book** — in an id group the keeper SHARES its id with the copies being dropped, so an unconditional `addTomb` would delete the keeper on the next sync. ## Recipes section — current shape
- Store: `fl4_recipebook` — **shared household-wide** (newest-wins-by-`updated` merge via `/shared`, plus same merge on the personal channel for same-account devices); separate from grocery-import `fl4_recipes`.
- Section headers: `<b>…</b>` / "Label:" lines render as sub-headings in the detail view and are excluded from the grocery list (`isHeaderIng`).
- List view: filter bar (All / ★ Favourites / per-category chips), grouped by category in All view.
- Detail view: servings stepper, ingredients (scaled per unit rules, **bulleted since v394**), **prep (v396 — the typed `prep` field if set, otherwise a list DERIVED from the ingredient lines at render time; never written to the record by rendering)**, method (**auto-numbered `<ol>` since v394 — `methodSteps` splits it, the stored text is never rewritten**), notes, **source link (v393, optional — shown only when set)**, fav star, **🛒 Add to grocery list…** (opens the v368 review screen, see below), Edit/Delete. A line whose shopping preference is set shows it quietly ("· not added to the shopping list" / "· bought as “X”").
- Editor: name, serves, category (datalist-suggested), **in rotation checkbox (v362, eligible for weekly auto-fill)**, ingredients (one per line "amount unit name"), **prep (v396, optional — never pre-filled; a "↓ Use the prep from my ingredients" button appends the derived lines when there are any)**, method, notes, **URL (v393, optional — auto-prefixed with `https://` via `normalizeRecipeUrl`)**.
- Import: ⬇ Import button → paste CSV → live "N recipes found" preview → Import. **Ids come from `nextRecipeId(recipeIdMap(book))` (v400)** — monotonic, checks ids already in use, reserves each one it hands out. **Never go back to a `Date.now() + index + random()` formula:** `Date.now()` is constant across an import loop, which collided on 99.9% of 118-recipe imports.
- **Duplicate repair (v401): a banner on the recipe list, shown only when duplicates exist.** Groups records sharing an **id** (the v400 bug — only the first was reachable by `find()`) and records sharing a **name** with different ids; a record is only ever in one group. Suggests the fullest copy via `recipeRichness()`, review-first, deletes with tombstones. **`applyDupRepair` must use `_dupState.book`, not a fresh `getRecipeBook()`** (that re-parses and returns new objects, so identity matching misses), and **must not tombstone an id that remains in the book** (an id group's keeper shares its id with the dropped copies).
- **Prep helper (v397, batched v398): recipe list → 📝 Prep helper.** Copy the recipes + an AI prompt to the clipboard → paste into a chat → paste the reply back → review per recipe (tick, edit inline, existing prep shown alongside) → Apply. **Batched by CHARACTERS — `PREP_BATCH_CHARS = 12000` via `prepBatchRanges()` (v399, replacing v398's fixed count of 20)** — recipes vary from three lines to a 4,000-character method, so a fixed count produced wildly different paste sizes; both the paste going out and the reply coming back get cut off when it's too big. A recipe bigger than the whole budget gets its own batch rather than being dropped. Applying a batch advances to the next one rather than leaving the screen. **A re-run pre-ticks nothing** (every recipe already has prep), which is deliberate — the Tick all / Untick all card explains it; do NOT "fix" it by pre-ticking rows that would replace what he wrote. **Writes ONLY `prep` + `updated`, never any other field** — that narrowness is the whole safety argument, so don't widen it without a fresh design call. **Reply format is `=== <id>` blocks, one prep step per line, asked for INSIDE a single code fence (v402 + v403)** — the fence is load-bearing, not cosmetic: it's what gives a chat reply a one-tap Copy button on a phone, and v402's "no code fence" wording was a regression. NOT JSON: an unescaped inch mark (`⅛" slices`) closes a JSON string and rejects the whole paste, and inches/quoted names are ordinary in recipes. The block format has no escaping at all and a truncated reply still imports its complete blocks. **JSON is still accepted as a fallback** (`recipe-prep-v1` tag) so a reply already in flight isn't stranded — don't delete that path. Matching by `id` with a name fallback via `matchPrepEntries()`, shared by both formats; invisible characters stripped before parsing (the v395 class of bug). Recipes still have **no general JSON export/import** — this is a one-field round trip, not a recipe file format.
- Unit rules: tsp/tbsp fixed; cups→g (dry) or ml (liquid); counts pluralise.
- Add-to-grocery: tag = recipe name; **amounts** carried as a separate `item.amount` field on grocery items, scaled to current servings (names-only fallback when no clean amount); saves a reusable chip at base servings.
- Week plan (v317): third recipe view ("📅 Week plan" button on the list) — 7 day cards (today..+6, dinner only), tap-to-assign from a favourites-first picker, per-day servings, "Add week to groceries" batch-calls the per-recipe flow with summed servings. Store `fl4_mealplan`, household-shared (newest-wins per day, no tombstones).
- **Canonical ingredient shape (v366): `"<amount> <unit> <Name> (<detail>)"`.** No per-ingredient note field exists or is needed — the bracket IS the note channel, because `cleanGroceryName` strips brackets out of the grocery name and `amtDetail` carries the text into the item's note. Anything new that writes an ingredient should emit this shape. `ingredientToLine(ing)` is the single serializer (headers re-emit as `<b>Name</b>`, fractions as fractions) and `parseIngredients` reads it straight back.
- **Tidy tool (v366): recipe list → 🧹 Tidy.** One-off maintenance pass that rewrites STORED ingredients into the canonical shape (everything before it — v363 cleanup, v365 rescue — was downstream-only and never touched storage). Review-first: tick per recipe, edit any line inline, nothing written until Apply; a line it can't rewrite losslessly is flagged "needs your eye" and left byte-identical. Step two offers to unify names that mean the same product. See the v366 changelog entry for the full safety model.
- **Grocery review screen + per-ingredient shopping preferences (v368).** "🛒 Add to grocery list…" opens a review step: tick what you need, and edit the **shopping name** (the name that lands on the list) per line. Both are stored on the ingredient — `groceryName` (override, used verbatim; wins over `splitGroceryName`'s derived name) and `noBuy` (never shop for this) — and remembered for every later add. **`groceryName` deliberately never rewrites the ingredient's own `name`**, so the recipe keeps its wording and nothing can be lost by a rename; `noBuy` is honoured on every path into the list (single recipe, week planner, roll-over) because they all go through `addRecipeToGroceries`. Read them with `recipeGroceryName(ing, sp)`. **Anything that re-parses ingredient text must call `carryGroceryPrefs(next, prev)`** or both fields are silently dropped (already wired into the editor save, `applyTidyLines` and `rescueIngredientMeasure`).
- Rotation + roll-over (v362): recipes carry `inRotation`/`lastCooked`; "🔁 Fill empty days" (planner button) and a weekly "New week — plan dinners?" banner both call `runMealPlanFill()`, which assigns least-recently-cooked in-rotation recipes to empty days in the window only — never auto-fires, always behind a tap. See the v362 changelog entry for full detail.

## CRITICAL technical quirks (these cause bugs if ignored)

1. **Duplicate function definitions (the old "38 duplicates" incident — deduped in v297; verify counts before editing).** Many Train/body/history functions once existed as TWO top-level copies, where the second silently won via hoisting — editing the first copy was a silent no-op. v297 deleted the last seven duplicate pairs (`trainTodayStr`, `trainShiftDay`, `trainFmtDate`, `trainFmtDateLong`, `timerCircle`, `wireInputs`, `wireWorkoutLog`), v339 removed the duplicated `openSetSheet`/`closeSetSheet` + `DOMContentLoaded` block, and **v351 removed the last duplicated region** (the 24-name workout-session block the v350 CI grep found, plus the duplicate `syncPaused`/`lastPushTs`/`syncPrefs` declarations) — **as of v351 every top-level function and var has exactly ONE definition, and the CI duplicate-grep allowlist is empty, so any new duplicate fails the PR checks.** Standing lesson stands: grep a function's definition count before editing it.

2. **Two real `<script>` blocks — syntax-check the RIGHT boundary.** The file has one external script (DOMPurify, self-closed) then the **main inline app block**; a third `<script>` appears only *inside a JS string* (the print-doc) and is not a real block. To check the main app code, extract from the `// PREVIEW MODE` comment to the **FIRST** `</script>` after it, then `node --check`. **Using the LAST `</script>` produces a convincing FALSE error** — it sweeps up the print-doc HTML string and other script blocks, and `node --check` reports a syntax error (often "Unexpected token '<'") that is NOT real. If a syntax error appears, first confirm you used the first-`</script>` boundary before chasing it. **Also: never hard-code the boundary line number from a previous version — every edit shifts line numbers, so a stale `sed -n 'A,Bp'` range will truncate the script mid-code and throw a false "Unexpected end of input". Re-derive the first-`</script>` line dynamically each time (e.g. `awk 'NR>=START && /<\/script>/{print NR; exit}'`) before extracting.**

3. **Python `str_replace` fails silently.** Always grep-verify a replacement actually landed (count occurrences before/after).

4. **Never write at a computed index without checking `find()` succeeded.** The v221 corruption came from a Python edit where `find()` returned −1 and the code then wrote at `idx + len(...)`, which appended a FULL DUPLICATE of the document after `</html>` — doubling the file to ~923k chars (two "Hearth" headers, raw `no-cache` meta visible as text, broken nav). If a find/anchor might miss, assert it found something before slicing/inserting.

5. **End-of-file edits are dangerous — verify structure after.** After ANY edit near the end of the file, verify: total length is sane (**~557k at v267, ~665k at v308, ~715k at v326**, growing slowly each version — a sudden jump to ~900k+ means the v221-style doubling), exactly ONE real `<html lang>`, ONE version string, DOCTYPE count of 2 (one real + one inside the print-doc JS string). The fix for the v221 doubling was truncating at the first `</body>\n</html>`.

6. **Scope: helpers called from top-level renderers must be top-level.** `renderList`, `openItemSheet`, `switchSection` etc. are top-level functions. A helper they call (e.g. `getTravelTags`, `renderItemSheetTags`) that is accidentally defined INSIDE a setup/IIFE block throws "X is not defined" the moment the renderer runs (this was the v226 bug). Define such helpers at top level.

7. **Bottom-of-page sheet wiring must run after DOM-ready or be null-guarded.** Several sheets (import, recipe import, item sheet) have their HTML near `</body>`, AFTER the main script. Code that calls `getElementById(...).addEventListener` on those elements at top-level script time hits `null` (the v235 crash). Either defer wiring with `DOMContentLoaded` (with an `else wire()` fallback if already loaded) or null-check every element before wiring.

8. **`confirmDialog` is OK/Cancel only.** It does NOT take custom button labels or a third option. When a 3-way choice is needed (e.g. recipe clear: delete added / keep added / cancel), hand-build a small overlay dialog — don't assume confirmDialog can do it.

9. **Check whether a feature already exists before building it.** This codebase has had features added across many sessions; some are present but not in any summary. Twice, work was started on something already built (list search; a collapse-arrow CSS rule). grep for the feature's likely identifiers first.

10. **`var history` conflicts with `window.history`.** Declaring `var history = []` (or any value) in browser global scope silently fails in some Android Chrome versions — `window.history` is a protected browser object and the assignment is ignored, so `history.sort()` later operates on the real `History` API and blows up. **Never use these names as global variables:** `history`, `location`, `name`, `status`, `frames`, `top`, `parent`, `self`. Use `hist`, `loc`, `roomName`, etc. instead. (Discovered building FreshList v3-v4; caused items to disappear after first add.)

11. **Firebase SSE self-echo race condition.** Every local push to Firebase triggers an SSE event back to the same device carrying the pre-push state. If that event is applied naively it overwrites locally-added items — the "items disappear after 8 additions" bug. The v245/v246 Hearth solution (union-merge + newest-wins + tombstones, apply immediately) already handles this correctly. If ever revisiting sync: **do not re-introduce a blanket grace-window that drops all SSE events** — it silently kills incoming changes from other devices. The right model is merge-then-re-push-if-fuller, not drop.

12. **Format toolbar on mobile goes at the bottom.** When building any rich-text editor with a toolbar, put the toolbar at the **bottom** of the screen. Android's native text-selection popup (Copy/Cut/Paste) appears near the selected text, which is usually in the upper part of the editor — directly over a top toolbar. Bottom toolbar avoids the collision entirely. Use `padding-bottom: max(10px, env(safe-area-inset-bottom))` to respect the home indicator on notch devices.

13. **PWA manifest icons must be real PNG files with separate `any` and `maskable` entries.** Using SVG data-URIs in manifest `icons` or combining `"purpose": "any maskable"` into a single entry prevents Chrome from showing the install prompt. Always generate actual `.png` files and list them as two separate objects:
    ```json
    {"src":"icon-192.png","sizes":"192x192","type":"image/png","purpose":"any"},
    {"src":"icon-192.png","sizes":"192x192","type":"image/png","purpose":"maskable"}
    ```

## Cross-app lessons (from My Health session, June 2026)

Lessons from a parallel vanilla React PWA session that apply equally to Hearth:

14. **`<\/script>` with a literal backslash causes a blank page with no JS errors.** Chrome's HTML parser looks for `</script` (case-insensitive) to close a script element. `<\/script>` — with a backslash — does NOT match, so external `<script src="…">` tags appear unclosed and the main inline script block never executes. The page renders blank and the console shows nothing from the app (only extension noise). This creeps in from editors or copy-paste that escape closing tags for use inside JS strings. Fix: `sed -i 's/<\\\/script>/<\/script>/g'` or a plain find/replace in the GitHub editor.

15. **Edge Tracking Prevention blocks unpkg.com/CDN scripts on `file://` URLs.** Microsoft Edge treats external CDN requests (React, etc.) as third-party trackers when the page is served from `file://`. Result: React never loads, page is blank. The tell is `"Tracking Prevention blocked access to storage for <URL>"` in the console — NOT a JS error. Fix: use Chrome for local PWA development, or serve via `npx serve .` on localhost.

16. **Browser extension errors in the console are not app errors.** The Apollo Client DevTools extension logs `content.js: ApolloClient connectToDevTools` on every page load regardless of what the page does. It is completely benign. In general, if an error references `content.js` and a line in the hundreds/thousands, it is an extension content script, not app code.

17. **Image-to-named-item mapping must always be user-verified.** Never guess photo→pose (or photo→anything) mappings from album order, filenames, or sequence. Always ask the user to open each URL and read the label/content directly. Wrong mappings are completely invisible at code time and only show up visually in the app.

18. **bash tools can go unavailable mid-session.** When `bash_tool` and `str_replace` become temporarily unavailable, present pending changes as clearly-labelled code artifacts with exact find/replace strings so the user can apply them manually or carry them to the next session. Never silently drop changes that were discussed but couldn't be applied.

19. **Per-leg/per-side timer pattern.** For timed physio/exercise exercises requiring separate timers per leg or side: add `sets:2, perLeg:true` to the exercise data object; in the UI, check `ex.perLeg` to show `"Right leg"` / `"Left leg"` instead of `"Set 1 of 2"` / `"Set 2 of 2"`. All other exercises with `perLeg` absent fall back to the normal set label automatically.
