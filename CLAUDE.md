# Hearth — agent project guide

Hearth is a family-hub PWA: one large single-file vanilla **HTML/JS** app, no build step, no framework.
Cathal is a **non-coder**; treat him as the reviewer, not a co-developer. Lead with the answer, be concise, flag honest trade-offs over overselling.

## Repo layout
- `index.html` — the entire app: HTML + one big inline `<script>` + CSS. This is where almost all work happens. It grows every version, so this file deliberately quotes no size — run `wc -lc index.html` if you need the number.
- `sw.js` — service worker. Single source of truth is its `VERSION` constant (cache name + the version label shown in-app both derive from it).
- `HEARTH-notes.md` — **read this at the start of any non-trivial task.** Architecture, sync model, storage keys, the per-change workflow, and a long list of hard-won "do/don't" lessons. Don't duplicate it here; consult it.
- `HEARTH-changelog.md` — detailed entries for the newest ~10 versions. **Don't read it end to end** — read only the entries for versions you're actually touching.
- `HEARTH-backlog.md` — pending work, triaged review findings, and decisions on record. Read when picking up new work or checking whether something was already built/rejected.
- `HEARTH-archive.md` — changelog entries older than the newest ~10, plus finished backlog items (§ Completed backlog items). Read it **only** when an old version is referenced.
- `HEARTH-data-models.md` — the per-store field lists (trip, plant, home inventory, health, test-build seed) and every place a new field must be added. Read the relevant section **before touching a field** — see § Data models below.
- Other `HEARTH-*.md` files are one-off design records and reviews (e.g. `HEARTH-cloudflare-access.md`, `HEARTH-firebase-rules.md`, `HEARTH-freeze-analysis.md`). Read one only when a note points to it.

  *(The changelog and backlog were split out of `HEARTH-notes.md` on 16/08/2026 — combined, that file had reached ~72k tokens, so reading it cost a third of a session's context before any code was opened.)*
- `.claude/` — cross-compatible workflow tooling used by Claude Code and every Cursor Agent model: `agents/hearth-preflight.md` + `agents/hearth-verifier.md` (both Haiku; subagents below), `agents/hearth-scout.md` (Sonnet, read-only code-location sweeps), `skills/release/` (explicit `/release` skill), `skills/hearth-council/` (council review).
- `.cursor/agents/` — thin Cursor-only wrappers around the three canonical `.claude/agents/` prompts. They pin preflight/verifier to Composer Fast and scout to Composer, avoiding unavailable Claude aliases without duplicating the prompts.
- `tests/` — zero-dependency behaviour test suite (since v350; see `HEARTH-notes.md` § Tests). Run `node tests/run.js` before committing.
- Hosted on **GitHub Pages**; `main` is live. No backend except Firebase Realtime DB (household sync via room codes, REST/EventSource — no SDK).

## Per-change workflow (every change)
1. **Run the `hearth-preflight` subagent before any edits** — every time, without exception. It confirms the base is the latest `origin/main` (one PR per version), pushes the `backup-vNNN` branch, reports version state, names backup branches outside the keep-newest-10 window for Cathal to delete, and greps for already-built features when given keywords. Resolve any flags before editing. Never touch `main` directly.
2. **Edit incrementally** — never rewrite the whole file. Make targeted edits. **Never read `index.html` in full** (over 1MB — most of a context window) — grep for the target function/text and read only the relevant line ranges. For broad "where is X / does X exist / who calls Y" sweeps, delegate to the **`hearth-scout` subagent** (Sonnet, read-only) and work from its line anchors — but always read the exact lines you're about to edit yourself; the scout finds code, it doesn't vouch for understanding it.
3. **After edits, before committing, run both: `tests/checks.sh` and `node tests/run.js`** — expect exit 0 from each. `tests/checks.sh` is the single implementation of the mechanical checks (script block syntax, DOCTYPE/version-label counts, clean EOF, the document-doubling ratio, version-bump consistency, the dosing literal pins, duplicate function names) and is **the same script CI runs**, so green locally means green on the PR. Then grep-confirm the strings you just edited actually landed — that's the one check no script can do for you, and silent no-op edits have caused real incidents here. The `hearth-verifier` subagent still exists and does exactly this, but it's now optional: two commands are usually faster to run directly than to delegate. **If a change touches anything under `tests/`, say so explicitly in the PR body** ("tests changed: which, why") — a behaviour change must never slip through disguised as a quiet test edit.
4. **Check `HEARTH-backlog.md` § Piggyback fixes** — a short list of verified stale lines waiting for a version that already touches their file. If yours does, fix the line in the same commit; if it doesn't, leave it. No version, PR or design confirm of their own. `tests/checks.sh` prints a `note pending piggyback fix` line for each one still outstanding.
5. **Bump the version in BOTH `index.html` and `sw.js`.** Format: `vNNN · DD/MM/YYYY` (date only, no time). For `sw.js` this is the one-line `VERSION` edit.
6. **Commit, push, then immediately open a GitHub PR** — always, without waiting to be asked. The PR is how Cathal reviews the diff and merges to `main`. **The canonical PR shape is `.github/pull_request_template.md`; the exact filling-in procedure is `.claude/skills/release/SKILL.md` step 7.** Follow those two — they are the single source of truth, and the API does *not* apply the template automatically, so reproduce it by hand. (These rules used to be written out in full here as well; three copies drifted, so this is now a pointer. Don't re-expand it.)

   Never push and say "create a PR when you're ready" — create it now. **One PR per version** (policy set 02/07/2026): Cathal merges within minutes, so never stack a second version onto an existing PR's branch — fetch/rebase onto the latest `main` before starting each new version, and open a fresh PR for it. The explicit `/release` skill automates the bump→verify→commit→push→PR tail; a GitHub Action re-runs the mechanical checks on every PR as a backstop.

## Design & safety rules (these override a prompt that conflicts)
- **Cursor model routing (06/09/2026).** Cursor's `.cursor/agents/` wrappers pin preflight/verifier to Composer Fast and scout to Composer; the canonical Claude Code agents stay on Haiku/Haiku/Sonnet. **Never change a routine support agent to `inherit`** — it would copy an expensive parent model. Never automatically launch Fable, Opus, GPT Sol at high/xhigh/max effort, or any current equivalent marketed as a frontier/highest-tier model as a child agent. Do not use Auto/Router when it may choose one of those models. If a pinned support model is unavailable, do not silently substitute a more expensive model: report it and let Cathal select an available same-tier replacement. Cursor has no project-configurable fallback list, so one exact pin per wrapper is deliberate.
- **Model check before risky/fuzzy work (Cathal's standing request, 05/07/2026; explicit-selection gate strengthened 06/09/2026).** Before building anything that touches sync/merge logic, medicine dosing, trip import/export, or the service worker — or any feature whose design is still fuzzy — say which model this session is running on. If Cathal did not explicitly start the parent session on a top-tier model (Fable/Opus or an agreed current equivalent), prompt him to restart the session on one (or use plan mode on the stronger model) and wait for his answer before building. **Do not satisfy this gate by launching a top-tier subagent** — the expensive model must be the parent session Cathal selected. Don't nag for small, well-defined changes — plain Sonnet or the routine Cursor equivalent is the right default for those. The rule runs both ways: if a session on Fable/Opus turns out to be a small, well-defined change, say so — but as **one line in the PR body**, not a paragraph in the changelog entry (16/08/2026; those retro notes were costing a paragraph of top-tier output per version). Finish the task either way, never stop work over it.
- **Design-here, build-there handoff (12/07/2026, gated 16/08/2026).** When a Fable/Opus design chat confirms a feature that won't be built in the same session, record every confirmed decision in the feature's entry in `HEARTH-backlog.md` — specific enough that a plain-Sonnet session can build it from the backlog alone — **and get that design PR MERGED before the build session starts.** v415 shipped the wrong thing because the design PR was never merged and `main`'s note stayed ambiguous. **Skip the split entirely** when the change touches sync/merge, dosing, trip import/export or the service worker, when the design is still fuzzy, or when the build is small enough to describe in under ~200 words (below that, writing the spec costs more than doing the work). This session-level split is the preferred model economy; do NOT delegate editing to a cheaper-model subagent inside a session instead (subagents stay read-only/checking: scout, preflight, verifier — the editing session must always read the lines it edits itself).
- **Confirm feature design before building anything non-trivial.** Cathal has corrected mid-build many times; align upfront.
- **Build the confirmed scope — no wider, no narrower (16/08/2026).** Deliver what was asked, at the scope intended. Make routine judgment calls yourself, and check in only when different readings of the request would lead to materially different work. If the request seems mistaken or a better approach exists, **say so in a sentence and continue with the task as asked** — don't quietly narrow, widen, or transform it. Finish the whole task and only report it done when it is; if part of it genuinely can't be finished, do the rest and say plainly what's missing and why. Stop short of changes clearly beyond what the ask implies. *(This is v414's failure written down: the confirmed design was "grow the `+` only, leave the `✕` at 32px", and the build grew both — an unconfirmed delete button made as easy to hit as the safe, frequent add. The design confirm covers where the work starts; this rule covers not drifting during it.)*
- **Don't add verification scaffolding to prompts or docs.** Instructions like "double-check your work" or "use a subagent to verify" make current models over-verify — they already re-check their own work, and the extra pass costs tokens without improving the result. The mechanical checks (`tests/checks.sh`, the test suite, CI) are deterministic and stay; what should never be added is an instruction telling the session to re-read its own reasoning.
- **Medicine dosing is safety-sensitive.** Weight-based doses use confirmed product strengths only (Calpol Infant 120mg/5ml @15mg/kg; Nurofen for Children 100mg/5ml @10mg/kg), round DOWN, cap at 10ml, block Nurofen under 5kg, always show the working + "check the leaflet", keep editable. Never silently change strengths or formulas. The v291 **interval advisories** (paracetamol ≥4h gap / max 4 per 24h; ibuprofen ≥6h / max 3 per 24h) are advisory only: never disable logging, never drop the "logged" / "check the leaflet" wording, never silently change the intervals.
- **Never claim a file/feature is missing without grepping first.** Check whether something already exists before building it (features have been rebuilt by accident here).
- This is a **personal/family app**: no Play Store, no push notifications, no third-party analytics. Don't propose them.

## Critical code quirks (full list in HEARTH-notes.md)
- `renderX()` functions rebuild their view from scratch — static HTML for those sections is dead code; put changes inside the render function.
- Helpers called from renderers must be **top-level**, not locally scoped.
- Guard `find()`/array lookups against `-1` (an unguarded `-1` once duplicated the whole document).
- A literal `</script>` inside a JS string breaks the HTML parser → blank page; the print-doc string escapes it as `<\/script>`.
- Avoid `var history` (shadows `window.history`).
- The in-app version label is set at runtime from the `sw.js` `VERSION` via postMessage — a stale-looking version means the new service worker hasn't activated yet, not a bug.

## Data models — read `HEARTH-data-models.md` before touching one
Each store below has fields hand-listed in several places, and missing one silently drops data on export, import or sync. **Before adding, renaming or changing a field on any of these, read that store's section of `HEARTH-data-models.md`** — it names every place the field must go:
- **Trip bookings** — export map in `openTripEditor`, `importTripFromJSON`, `mergeBookingsIntoTrip` (all three, same change).
- **Plants** (`plant-v1` files) — `PLANT_SECTIONS` plus the scalars in `plantExportObj` + `plantApplyImport`; multi-plant import matches by exact name only, never fuzzy.
- **Home inventory** (`inventory-v1`) — five hand-listed places plus `buildTestSeed`.
- **Health** (`fl4_health`) — one store with a `kind` field, never split per kind; `HEALTH_KIND_FIELDS` is the table; `files`/`phone` are the only hrefs and each has exactly one gate (`applianceLinkUrl`, `healthPhoneHref`).
- **Test-build demo data** — **a new section or store needs demo content in `buildTestSeed()` in the same change**; `resetTestData()` must wipe and reload, never seed the live page.

Everywhere: **a cleared field stores `""` (or `[]`), never a dropped key** — the merges refill `undefined` keys from the other device (the v296 rule).

## After significant work
Update the docs so the next session starts current — see `HEARTH-notes.md` § Maintenance habit for which of the three files changes and what goes in each. **Changelog entries are capped at ~150 words** (plus every "do NOT simplify this into X" warning, which is exempt); the full reasoning belongs in the PR, which is permanent and searchable.
