One-line change (index.html, in the `DOMContentLoaded` recipe-search wiring block, ~line 11313). No data-model, sync, or export changes. **Tests:** no test file changed — this is DOM/render-state wiring the `file://` harness doesn't specifically cover (same class as other UI-timing fixes); `node tests/run.js` re-run as-is, 27/27 files green (no regression). Verifier: SAFE TO COMMIT. **Also discussed:** revisiting **global search** (parked backlog item, see External review triage note above) — flagged to Cathal as fuzzy/undecided design work per the standing model-check rule; no design session held yet, recommended he open a fresh Fable/Opus session for that when ready. - **v378:** **Plant import/export — the AI round-trip (Cathal's ask 02/08/2026; designed + built on Opus, 3 decisions confirmed via AskUserQuestion).** He asked for the flow he already uses for trips, applied to plants: photograph a plant, have an AI chat write the care sheet from the photo + his own notes, get a file back, paste it into Hearth and have it fill in the sections. **Confirmed decisions:** ① **two-step import, ask each time** (paste → choose "Add as a new plant" or "Update <existing>") rather than always-new or silent name-matching; ② **"file wins, blanks left alone"** — a section the file fills in replaces what's there, a section it leaves `""` keeps the existing text (so re-running a better write-up over a rough note works, and a thin file can't wipe good notes); ③ **per-plant export + "Export all plants"**, the latter as a shareable care-book file, NOT a backup (the Settings backup is still the only thing that carries photos and logs). **File format `plant-v1`**, deliberately the trip-importer's shape: a bare plant object *or* `{"hearth":"plant-v1","plants":[…]}`, so a one-plant chat reply and a whole-book export come through the same door. **What is NOT in the file, by design:** `id` (regenerated), `updated` (set to now), `photo` (a chat can't write one, and base64 would swamp the paste box) and `waterLog`/`feedLog` (own history, not care information) — so an update **never** touches the photo or the logging streak, which is the promise the UI makes on that screen and is pinned by tests. **Field mapping is PLANT_SECTIONS-driven** — export, import and the AI prompt template all iterate the same table, so a ninth section stays a one-line change; only the six scalars (`name`/`latin`/`room`/`emoji`/`waterDays`/`feedDays`) are hand-listed, in `plantExportObj` + `plantApplyImport`, and both must be updated together (noted in `CLAUDE.md` alongside the trip rule). **The prompt template is the feature's real payload:** `plantAIPrompt()` builds it from `PLANT_SECTIONS` (skeleton JSON + one guidance line per section, using each section's own `hint`), so it can never drift from what the parser accepts; a "📋 Copy the prompt" button puts it on the clipboard (`navigator.clipboard` with an `execCommand` fallback — writeText needs a secure context and a gesture), with the full text also visible under a `<details>` for anyone who'd rather select it. Tests assert the skeleton is valid JSON, contains every section key, and carries no HTML entities (PLANT_SECTIONS labels are HTML source — `&amp;` is decoded for the plain-text prompt). **Defensive parsing throughout:** ```json fences stripped before parsing (chats add them even when told not to), wrong-tag files rejected by name (a trip file is not a plant file), null/non-object array entries dropped, every section capped at `PLANT_FIELD_MAX` (4000 chars) so a runaway reply can't eat localStorage, intervals coerced/clamped to 0–365 with junk text → 0 ("no reminder") rather than NaN, and `importPlantInto` guards the `findIndex` `-1`. Interval semantics: a field the file **omits** keeps its old value, but an explicit `0` is a real instruction and clears the reminder. **UI:** 📥 button in the plants header (mirroring trips), export buttons on the detail view and under the list, and `_plantImporting` added to the `flushSyncRenders` guard — the import screen holds pasted text that isn't saved yet, so an incoming sync must not redraw it away (the trip importer still has this gap; worth copying back if it ever bites). The import/export + fuzzy-design triggers made Opus the correct default under the standing rule, and the file-format and update-rule decisions were genuinely material — but with those three answers in hand the build itself would have been fine on Sonnet.

- **v376:** **Release E of the startup-freeze fix plan (`HEARTH-freeze-analysis.md`, claim 8) — the test harness can now register a real service worker, and the boot/update/dead-network scenarios are covered for the first time (3 design calls confirmed by Cathal via AskUserQuestion, 01/08/2026; designed + built on Opus).
