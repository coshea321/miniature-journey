  - **Dashboard reality for steps 4–6 (12/08/2026) — three things the written plan got wrong, all cost real time.** ① **"Self-hosted" is now "Self-hosted and private."** *Add an application* → the button reads **Continue with Self-hosted and private**; the "Example configuration: Public DNS" dropdown above it is an illustration only and configures nothing. "Private" means access-controlled, not tunnel-only. ② **The Domain dropdown will NOT offer `pages.dev`** — it lists only zones on your own account, and `pages.dev` is Cloudflare's. Use the **"Switch to custom input"** link under the Subdomain/Domain fields and type the full hostname. That link is the entire answer to the custom-domain question. ③ **Do NOT use the Pages project's "Preview access" toggle** (*Workers & Pages → project → Settings → General*). Its own help text says it protects **preview deployment URLs only** — "Production pages.dev and custom domains are managed separately in Zero Trust." Community posts recommending it for production are out of date; the Zero Trust application is the correct and only mechanism. Session duration and the policy both live on the application-creation screen, so steps 4/5/6 are one screen, not three.
  - **⚠️ The service worker makes a live gate look broken — expect this, do not chase it.** Hearth's SW serves the shell **cache-first** since v373, so any browser that has opened the URL before answers from its own cache with **no network request at all** — Cloudflare never sees it and the app loads ungated. This burned a whole diagnostic round on 12/08/2026 and nearly led to buying a custom domain that was never needed. **Test the gate only in a browser or device that has NEVER opened the URL** (a different browser, or a phone on mobile data). The same mechanism means **already-installed devices keep opening the app from cache after the gate goes live** — Access cannot intercept a request that never leaves the phone — so at step 7 everyone must add the app to their home screen **fresh** from the gated URL, and "it opened without asking for a PIN" on an old install is not evidence the gate is off.
  - **Two gotchas found while doing it (11/08/2026), neither in the original plan.** ① **The dashboard steers you into Workers, not Pages.** Cloudflare's "import a repository" flow now lands on the Workers builder — the tell is a **Deploy command** field pre-filled with `npx wrangler deploy` and no *Build output directory*. That flow fails for Hearth (no `wrangler.toml` in the repo). Pages is a separate, less prominent route: **Workers & Pages → Create → Pages tab → Connect to Git**; you're in the right place when you see *Build output directory* and no Deploy command. (The fallback if Pages ever disappears is Workers static assets, which needs a small `wrangler.jsonc` committed — not needed, not done.) ② **`_isTestBuild` had to be fixed BEFORE step 3 could prove anything** — see v418 above. Any future origin change hits this same guard first.
  - **⚠️ INCIDENT 11/08/2026 — the demo household reached real data. Read this before touching origins again.** Sequence: the Pages URL was opened *before* v418, so as a **test build** it seeded the fixed demo household into that origin's `localStorage`. v418 then made that hostname **production** — and **nothing wipes a test-build store when its host is promoted**, because `wipeTestStore()` only ever runs inside `_isTestBuild` (`index.html`, phase-1 block). The app booted as the real app holding demo data, login succeeded, `_personalFetchOk` flipped true, and `pushPersonal()` PUT the merged real+demo blob to Firebase, which the GitHub Pages devices then pulled. **Nothing real was destroyed** — the merges are additive by id and the seed writes no tombstones — **except the meal plan**, which merges newest-wins per *day*, so demo entries displaced the real plan on three days. Recovery was a **guided hand-delete** (deleting in-app writes tombstones, which propagate; `importBackupData` is additive by id, so restoring a backup *on top* would NOT have removed the demo records). Demo records are identifiable: **`_tsId()` returns `900000000000 + n`** while real ids are `Date.now()`-based (~1.7e12). **`pushHousehold`'s missing read-first guard was the amplifier and is fixed in v419** (above). **Both halves are now fixed: `pushHousehold`'s missing read-first guard (the amplifier) in v419, and a test-build store surviving its host's promotion (the root cause) in v420 — a banner that stops the device sending, with clearing on a tap. Cathal chose the banner over a boot-time wipe; see the v420 entry.**
